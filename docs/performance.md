# Аудит производительности

Автоматический аудит production-сборки с помощью [Lighthouse CI](https://github.com/GoogleChrome/lighthouse-ci) (`@lhci/cli`, Lighthouse 13). Настройки — в [`lighthouserc.cjs`](../lighthouserc.cjs).

Аудит работает локально и не обращается к внешним сервисам: отчёты сохраняются только на диск, аналитика и счётчики не используются. Деплой на Vercel и CI для этого проекта **пока не настроены**; ниже описано, как подключить аудит, когда они появятся.

## Запуск

```bash
npm run test:e2e:install   # один раз: Chromium от Playwright (если ещё не установлен)
npm run perf               # сборка + 3 прогона Lighthouse + проверка порогов
```

`npm run perf` выполняет `npm run build`, поднимает локальный статический сервер для `dist/` со сжатием gzip, трижды прогоняет Lighthouse и сравнивает медиану с порогами. Занимает около минуты.

- **Код выхода 0** — бюджеты регрессий соблюдены (предупреждения при этом допустимы).
- **Код выхода 1** — нарушен хотя бы один бюджет (`×` … `failure` в выводе).
- **Отчёты** — `.lighthouseci/reports/*.report.html`: откройте в браузере, чтобы увидеть подробности и подсказки. Папка не попадает в Git.

Браузер выбирается так: переменная `CHROME_PATH` → Chromium из Playwright → установленный Google Chrome.

## Что измеряется

Только категория **Performance**: доступность уже проверяется axe в `npm run test:e2e`.

Профиль — **мобильный по умолчанию в Lighthouse**: экран телефона, симулированный медленный 4G (~1,6 Мбит/с, RTT 150 мс) и замедление CPU в 4 раза. Это строже, чем настольный профиль, и соответствует тому, как Google оценивает мобильную версию.

| Метрика                                    | Что означает                                               | Связь с Core Web Vitals                                                    |
| ------------------------------------------ | ---------------------------------------------------------- | -------------------------------------------------------------------------- |
| **LCP** (Largest Contentful Paint)         | Когда отрисован самый крупный элемент первого экрана       | Core Web Vital                                                             |
| **CLS** (Cumulative Layout Shift)          | Насколько «прыгает» вёрстка при загрузке                   | Core Web Vital                                                             |
| **TBT** (Total Blocking Time)              | Сколько времени главный поток занят и не реагирует на ввод | Лабораторная замена **INP**: INP измеряется только на реальных посетителях |
| FCP (First Contentful Paint)               | Когда появился первый контент                              | Вспомогательная                                                            |
| Speed Index                                | Как быстро заполняется видимая часть экрана                | Вспомогательная                                                            |
| Вес страницы, размер JS, сторонние запросы | Бюджеты ресурсов                                           | Влияют на LCP и TBT                                                        |

Это **лабораторные** данные. Полевые Core Web Vitals (реальные посетители, INP) собираются только аналитикой на сайте, которая в проект намеренно не добавлялась.

## Пороги

Пороги разделены на два уровня.

**Бюджет регрессий (`error`)** — не даёт ухудшить текущее состояние. Значения заданы с запасом от базовой линии, чтобы проверка ловила заметные ухудшения, но не падала от обычного разброса.

| Проверка          | Порог    | Базовая линия (медиана) | Почему так                                        |
| ----------------- | -------- | ----------------------- | ------------------------------------------------- |
| Performance score | ≥ 60     | 72–75                   | Запас ~15 пунктов на разброс TBT                  |
| FCP               | ≤ 1,8 с  | 0,76 с                  | Граница «хорошо» по Lighthouse                    |
| LCP               | ≤ 20 с   | 17,0 с                  | +17 % к текущему: ловит утяжеление первого экрана |
| CLS               | ≤ 0,1    | 0                       | Граница «хорошо»; метрика детерминирована         |
| TBT               | ≤ 600 мс | 50–345 мс               | Граница «плохо»: TBT сильно зависит от CPU машины |
| Вес страницы      | ≤ 6,5 МБ | 5,5 МБ                  | +19 %                                             |
| JavaScript        | ≤ 100 КБ | 74 КБ                   | Размер после сжатия                               |
| Сторонние запросы | 0        | 0                       | На сайте нет внешних скриптов и сервисов          |

**Цели (`warn`)** — «хорошие» значения Core Web Vitals. Сейчас часть из них не достигнута, поэтому они выводятся предупреждениями и не роняют проверку:

| Цель                                            | Значение      | Сейчас                     |
| ----------------------------------------------- | ------------- | -------------------------- |
| Performance score                               | ≥ 90          | 72–75                      |
| LCP                                             | ≤ 2,5 с       | 17,0 с                     |
| TBT                                             | ≤ 200 мс      | 50–345 мс                  |
| Speed Index                                     | ≤ 3,4 с       | ~0,8–1,9 с                 |
| Доставка изображений (`image-delivery-insight`) | без замечаний | возможная экономия ~4,3 МБ |

Главная причина медленного LCP — фотографии в PNG весом 0,4–1,4 МБ. На первом экране телефона LCP-элемент — фото в hero (810 КБ). Сжатие фото и перевод в WebP/AVIF с адаптивными размерами — основной резерв. По мере улучшений поднимайте бюджеты в `lighthouserc.cjs` ближе к целям: например, LCP `20000 → 4000`, затем `→ 2500`.

### Зависимость от окружения

- **FCP, LCP, Speed Index и вес страницы** при симулированном троттлинге рассчитываются по загруженным байтам и почти не зависят от машины: разброс LCP между прогонами меньше 0,1 %.
- **TBT и общий балл** зависят от скорости CPU. На медленном или загруженном CI-раннере TBT растёт, поэтому порог TBT в бюджете — граница «плохо», а не «хорошо». Для устойчивости берётся медиана трёх прогонов.
- **Локально и на Vercel цифры будут разными.** Локальный сервер отдаёт файлы с gzip без CDN, Vercel — с brotli, HTTP/2 и кешем на CDN. Лабораторный аудит отвечает на вопрос «не стало ли хуже», а не «какие цифры будут у посетителей».

## Как интерпретировать результат перед деплоем

1. **Есть `failure`** — регрессия. Откройте HTML-отчёт: блоки _Insights_ и _Diagnostics_ показывают, что именно стало тяжелее (новое изображение без сжатия, крупная зависимость, сдвиг вёрстки). Исправьте или осознанно поднимите порог в `lighthouserc.cjs` с объяснением в комментарии.
2. **Только `warning`** — состояние не хуже базового. Предупреждения показывают, сколько осталось до «хороших» Core Web Vitals.
3. **Предупреждений нет** — цели достигнуты; перенесите соответствующие пороги из уровня `warn` в `error`, чтобы закрепить результат.

## Подключение к CI и Vercel в будущем

Ничего из этого сейчас не настроено.

- **CI перед деплоем.** Добавьте в workflow шаги `npm ci`, `npx playwright install --with-deps chromium` и `npm run perf`. При `CI=true` Chrome запускается с `--no-sandbox`, как требуется в контейнерах Linux.
- **Проверка развёрнутой копии.** Когда появится preview-деплой Vercel, аудит можно направить на его адрес вместо локальной сборки: `LHCI_URL=https://<адрес-preview> npx lhci autorun` (без `npm run build`). Если preview защищён авторизацией Vercel, понадобится токен обхода защиты; добавлять его стоит только в секреты CI.
- **Не встраивайте аудит в команду сборки Vercel** (`npm run build`): в сборочном окружении Vercel нет Chrome, а сборка не должна зависеть от измерений.
- Отчёты по умолчанию сохраняются только локально (`upload.target: 'filesystem'`). Не переключайте его на `temporary-public-storage`: тогда отчёты будут загружаться в публичное хранилище Google.
